## 3. Предметная область и суть сервиса

Сервис условный: реального заказчика нет, провайдер вымышленный/обобщённый.

Основной сценарий обработки обращения:
1. **Клиент создаёт обращение.** Основной канал: онлайн (веб).
   Канал «по телефону» **под вопросом**: возможно, в работе останутся только онлайн-обращения. Если телефон останется, нужно решить, вносит ли его оператор вручную или нужно распознавание речи.
2. **Система формирует ответ автоматически** на основе ИИ («умная система»).
3. **Оператор может изменить ответ** для конкретного клиента перед отправкой или после неё.
4. **База знаний обновляется автоматически**: система сама пополняет и корректирует базу знаний в зависимости от обновлений, изменений условий эксплуатации, новых типовых проблем и т. п.

Пользователи системы: **клиенты** провайдера (основная роль). Оператор упоминается как роль, которая корректирует ответы; уточнить, нужны ли другие роли (администратор, руководитель).

### ИИ-составляющая
- Используется **локальная модель, полностью обученная автором**, а не готовая LLM из внешних сервисов (не GigaChat, YandexGPT, OpenAI, Claude и т. п. по API).
- Открытые вопросы для проработки: тип задачи (классификация обращений, поиск по базе знаний, генерация ответа или их сочетание), архитектура модели, данные для обучения (откуда брать при условном заказчике), метрики качества, механизм дообучения/обновления базы знаний, способ интеграции с PHP-приложением (например, отдельный сервис на Python).

## 8. Правила для агентов

### Общие
- Пиши **на русском языке**, если автор не попросил иное.
- Перед работой прочитай этот файл и содержимое `материалы/`. Требования методички ОГУ важнее общих правил.
- Не делай больше, чем просят. Сейчас этап сбора материалов: текст ВКР и код не пиши без прямой просьбы.
- Перед крупными изменениями (переписать главу, удалить или переместить файлы, сменить стек или архитектуру) спроси автора.
- Не удаляй файлы автора. Новые версии сохраняй рядом или с пометкой, а не поверх.
- Если чего-то не знаешь (дата, требование, ФИО), не выдумывай: отметь `[уточнить]` и спроси.
- Открытые вопросы фиксируй в `заметки/открытые-вопросы.md`.

### Текст ВКР
- Научный стиль: безличные конструкции, без разговорных оборотов, без «я» (допустимо «в работе», «автором»).
- Оформление по методичке ОГУ; при её отсутствии ориентируйся на ГОСТ 7.32-2017 (структура и оформление отчёта) и ГОСТ Р 7.0.100-2018 (библиографическое описание). Сверь с методичкой, когда она появится.
- Текст должен быть оригинальным и проходить проверку на антиплагиат: не копируй чужой текст, перефразируй и ссылайся на источник.
- Каждая фраза с фактами, цифрами, определениями должна иметь ссылку на источник.
- Связывай теоретическую часть с практической: выводы глав должны обосновывать проектные решения.
- Не забывай про обязательные элементы магистерской работы: актуальность, объект и предмет, цель и задачи, научная новизна, практическая значимость, апробация (если требуется).

### Источники
- **Никогда не выдумывай источники**, авторов, DOI, страницы и цитаты. Добавляй только то, что реально проверено (открыто, найдено по ссылке).
- Предпочитай свежие источники (последние 5 лет), научные статьи (eLIBRARY, КиберЛенинка, Google Scholar, arXiv), ГОСТы, официальную документацию (Laravel, PostgreSQL и т. д.), отраслевые отчёты по телеком-рынку РФ.
- Для каждого источника сохраняй в `источники/`: полное библиографическое описание, ссылку, дату обращения и 1–3 строки, чем он полезен для ВКР.
- Количество источников в списке литературы: уточнить по методичке.

### Код (когда начнётся разработка)
- Работай в репозитории, ссылку на который укажет автор; в этой папке код не храни.
- Придерживайся стека из раздела 4; замены технологий согласуй с автором.
- Следуй соглашениям Laravel (PSR-12, миграции, сервисный слой, тесты).
- Модель ИИ должна быть собственной и локальной; не подключай внешние LLM API как основное решение.
- Описывай архитектурные решения так, чтобы их можно было перенести в текст ВКР (диаграммы, обоснования выбора).

### Проверка работы целиком
- Сверяй: тема ↔ цель и задачи ↔ содержание глав ↔ реализованный функционал ↔ выводы.
- Проверяй оформление по методичке, нумерацию рисунков/таблиц, ссылки на источники и список литературы.
- Результат проверки оформляй списком замечаний с указанием места, не правь текст молча.
